\section{System Architecture}

The proposed system adopts a modular architecture consisting of five main stages: Data Acquisition, Data Processing, Data Storage, Analysis Engine, and Application Layer. The implementation focuses on building a robust data pipeline that aggregates property information from multiple sources into a unified repository.

\subsection{Data Acquisition}
The system targets four major real estate portals in Singapore: PropertyGuru, 99.co, EdgeProp, and SRX. Specialized web scrapers are developed for each platform to extract granular data, including listing titles, prices, property attributes (size, bedrooms, tenure), and location details.

\subsection{Data Processing and Aggregation}
Raw data fetched from different sources frequently contains inconsistencies and duplicates. The processing module performs the following tasks:
\begin{itemize}
    \item \textbf{Normalization:} Standardizing field names and formats (e.g., converting "2 beds" and "2 Bedroom" to a standard integer format).
    \item \textbf{Deduplication:} Identifying and removing duplicate listings based on composite keys (e.g., address, unit size, and price) to ensure data integrity.
    \item \textbf{Linking:} Associating temporary rental/sale listings with persistent property master records (HDB or Condo units).
\end{itemize}

\subsection{Data Storage}
The data storage layer is built upon a PostgreSQL relational database, designed to maintain data integrity while supporting complex analytical queries.

\section{Database Design}

A relational database schema is designed to store both static property information and dynamic listing data. The core tables are structured as follows:

\subsection{Property Master Tables}
To maintain a definitive registry of properties, we define master tables for Housing Development Board (HDB) flats and private condominiums:
\begin{enumerate}
    \item \textbf{hdb\_basic:} Stores block-level information for HDB estates (e.g., address, completion year, lease start date).
    \item \textbf{hdb\_unit:} Stores unit-level details, linking specific units to their respective blocks.
    \item \textbf{condo\_basic:} Stores project-level information for condominiums (e.g., project name, developer, facilities).
    \item \textbf{condo\_unit:} Stores specific unit details within each condominium project.
\end{enumerate}

\subsection{Listing Tables and Association}
The \texttt{unified\_listings} table aggregates active rental and sale listings from the web scrapers. A key design consideration is the association between these transient listings and the master tables.

\begin{itemize}
    \item \textbf{Association Logic:} Since online listings provided by agents often lack specific unit numbers for privacy reasons, a direct foreign key constraint is not always possible during the scraping phase.
    \item \textbf{Agent-Assisted Mapping:} The system supports a "soft link" where the association between a listing and a specific physical unit (e.g., in \texttt{hdb\_unit}) is finalized when an agent arranges a viewing or verifies the property documentation. This design allows for flexible data ingestion while enabling precise tracking as the transaction progresses.
\end{itemize}
